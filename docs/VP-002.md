# VP-002 — Sparse MoE computational structure and bounded execution frontier

**Status:** implemented architectural reference, route reconstruction and bounded typed frontier. **No pretrained tensor payloads loaded; no transformer forward pass, expert kernel or completed LLM inference is claimed.** This is the first admission/dispatch prerequisite for a genuinely large-scale E-CPU-hosted model.

## Why MoE rather than another small-model prototype?

Decoder-only dense GPT-2 graph projection is already explored in E-CPU/HFR-002. The next research question is whether E-CPU can **address and schedule** a large neural system with many possible tensor operators while only a sparse subset is active for each token, and do so without one host materializing every expert.

Those *configuration-derived* tensor shapes are not a certificate of the source weight checkpoint, which must eventually be checked against a full pinned Safetensors manifest.

## The computational structure

The model Ground names the model, pinned source revision, exact profile fields and a canonical digest. A lazily addressed tensor reference gives its expected shape, tensor name, element count and dtype without allocating weights. All 12,032 expert instances of the 235B profile can therefore be addressed with bounded work and no tensor bytes.

For each layer and token, `route_experts` accepts a **complete externally supplied router-logit vector** (128 finite values), performs stable softmax, picks the top 8 experts, and applies the model's `norm_topk_prob` renormalization. Ties break deterministically by expert index for the reference implementation. A route receipt binds the Ground digest, full score vector, token position, layer, selected experts, normalized weights and expected tensor addresses. An independent verifier recomputes routing: rehashing a forged list of selected experts is not sufficient to pass.

An optional weight-manifest digest is only a caller-supplied reference and **does not authenticate or load weights**. It must not be interpreted as proof that the router scores came from the model. Routing uses Python reference float64 values; an actual bfloat16 model needs explicit numerical tolerance and deterministic comparison policy.

`compile_layer_frontier` converts one verified route receipt to **25 dependency-ordered tasks**, including RMSNorm, Q/K/V projection, per-head RMSNorm, rotary application, KV append, grouped-query attention, attention residual, sparse expert dispatch, selected SwiGLU experts, weighted reduction, and layer output. The graph is a *typed plan*, not actual executed neural operations. It is intentionally layer-local to avoid E-CPU's present 256-node global-DAG bound; successive layer frontiers can be scheduled and committed separately once native numerical operators exist.

### Concrete source of truth / reproduction

From the repository root, with Python 3.11+:

```bash
python -m unittest discover -s tests -p 'test_moe.py' -v
python -m vp.moe describe --model qwen3-235b-a22b
python -c 'import json; print(json.dumps([float(i % 13) for i in range(128)]))' > synthetic-router.json
python -m vp.moe route --model qwen3-235b-a22b --layer 93 --token 40959 --logits synthetic-router.json > route.json
python -m vp.moe verify --model qwen3-235b-a22b --receipt route.json
python -m vp.moe frontier --model qwen3-235b-a22b --receipt route.json > frontier.json
```

**Synthetic-router.json is a synthetic test fixture.** The command above does not infer a token or obtain router logits from real weights. It tests exactly what the exported E-CPU operator description and verifier are willing to admit.

## Resource accounting, not invented performance

The 235B-profile inferred parameter inventory is about 235.09 billion declared parameter elements / 470.19 GB bfloat16 payload, which is architecture-derived, not a downloaded checkpoint verification. Only eight of 128 experts are selected at a layer. The **distinct parameter elements associated with a token's active operations** are therefore fewer than the total, but that is not a guarantee of physical bytes transferred, available bandwidth, residency, latency, or speedup.

KV-cache size at full 40,960-token context under the declared four KV heads / 128-head-dim / 94-layer / 2-byte model is **7,885,291,520 bytes** (single sequence, no allocator overhead). The representation can be partitioned or checkpointed, but no transfer or recovery of those tensor pages is implemented here.

## Unfinished numerical contract

This milestone does not yet:

1. Retrieve and authenticate the original model's full weight tensor inventory or tokenizer.
2. Compute routing logits, RoPE, GQA, SwiGLU, residuals, or next-token probabilities from those weights.
3. Convert frontier task descriptions to E-CPU `NavigableComputationDAG` executable nodes with Hypervisor-governed tensor operators.
4. Prove numerical equivalence across bfloat16, quantized, or multi-host realizers.
5. Perform physical inter-host expert execution or demonstrate *communication-path substrate computation*.
6. Commit a real generation checkpoint and resume autoregressive inference after host loss.

Those are the next gated milestones. Start by executing **one complete layer frontier from actual verified weights**, obtaining real router logits, numerical references, and operator receipts. Only then admit a genuine next-token or multi-host model execution. E-CPU's existing `ComputationalObjectStore`, Neural Graph Bridge, E-GPU, Virtual Layer, and recovery lineage are to be reused rather than duplicated.
